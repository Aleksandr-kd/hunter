### Стратегия монетизации: бесплатный период → подписки (когда появится ИП)

> ⚠️ **Контекст:** сейчас у автора нет ИП, поэтому монетизация не подключается.
> Приложение публикуется бесплатно, всем пользователям открыты **все** функции.
> Позже, когда появится ИП, включаются подписки. **Необходимо сохранить
> «грандфазеринг» (grandfathered)**: пользователям, установившим приложение до даты
> перелома (`T`), навсегда остаются те функции, что они видели в бесплатный период.
> Новым пользователям — по подписке. Это снижает негатив и отвалы.

**Выбрать дату перелома (T):**
- [ ] Зафиксировать дату `T` (момент первого релиза с включёнными подписками)
- [ ] Добавить в `profiles` (или в `subscriptions`) поле даты создания аккаунта / установки, чтобы отличать «до `T`» и «после `T`»

**Грандфазеринг (один раз, на стороне бэкенда Supabase):**
- [ ] Для всех пользователей, зарегистрированных до `T`, проставить в таблице `subscriptions` `/ profiles` `tier = 'max'` (или `grandfathered = true`) — **раз и навсегда**
- [ ] Убедиться, что `expires_at` для grandfathered не ставится (или ставится на 2030+), чтобы логика `AuthProvider.loadSubscription()` не сбрасывала их в `none` по просрочке
- [ ] Новым пользователям (после `T`) — `tier = 'none'`, обычные лимиты

**Код (клиент) — почти не меняется, т.к. гейтинг уже заложен:**
- [ ] Уже есть: `AuthProvider.loadSubscription()` читает `tier` из Supabase и применяет `isPremium` / `isMax`, лимиты дневника, тёмную тему
- [ ] Для grandfathered `tier='max'` — приложение автоматически даст все функции без подписки
- [ ] Для новых `tier='none'` — включить кнопки подписки (см. «Интеграция RuStore SDK» ниже)

**Проверки перед выпуском обновления с подписками:**
- [ ] Старый пользователь (до `T`): видит все функции, кнопки «Подключить» скрыты/неактивны
- [ ] Новый пользователь (после `T`): видит лимиты и кнопки подписки
- [ ] `flutter analyze` и `flutter test` — без ошибок
- [ ] Обновление выкатывается как обычный релиз в RuStore (без удаления данных)

## БАГ #1b (2026-09-01) — фото не обновляется на другом устройстве без выхода из аккаунта

> Найден при ручном тестировании после исправления БАГ #1.
> Данные на сервере правильные, но realtime не срабатывает — фото обновляется
> только после выхода и повторного входа (когда DiaryProvider инициализируется заново).

- **БАГ #1b (Medium)** — после upload записи с новым фото realtime-событие не
  доходит до других устройств (возможно из-за RLS-политик Supabase). Фото

## БАГ #3 (исправлен 2026-09-01) — локальный `photo_url` не обновляется после смены фото

> Найден в полном регресс-QA (2026-09-01) при ревью цепочки «смена фото → upload →
> запись в локальную БД». Отличается от уже исправленных БАГ #1/#4 тем, что те
> покрывали только серверную часть (`photo_url` на сервере и на другом устройстве),
> а локальная запись на устройстве-редакторе не проверялась.

- **БАГ #3 (Medium, исправлен)** — после СМЕНЫ фото при редактировании локальная запись
  в БД оставалась с `photo_url = null`, хотя на сервер уходит новый URL.
  Причина: `DiarySyncEngine._pushWithPhoto()` создаёт обновлённую копию
  (`entry.copyWith(photoUrl: url)`) как **локальную переменную** `updatedEntry` и
  возвращает только `bool`. Вызывающий `_uploadEntry()` затем записывает в БД
  `photoUrl: entry.photoUrl` (исходный, == null после смены фото в `_save()`),
  а не новый URL. Тот же эффект в цикле `sync()` (строки 375–401).
  **Исправлено:** `_pushWithPhoto()` теперь возвращает `DiaryEntry?` (обновлённую запись
  с актуальным `photoUrl`), публичный `pushEntry` остался `bool`, добавлен
  `pushEntryWithPhoto()`. `_uploadEntry()` (engine) и цикл `sync()` пишут в БД
  `updated.photoUrl` (новый URL) из возвращённой записи. Аналогично исправлен
  `DiaryProvider._uploadEntry`, который теперь использует `pushEntryWithPhoto`.
  Покрыто юнит-тестами: `test/providers/diary_provider_bugs_test.dart` (группа «БАГ #3»,
  2 теста: локальный photoUrl после upload == новый URL; `pushEntryWithPhoto` возвращает
  запись с новым URL).

- **Замечание (Low)** — тесты на смену фото проверяли сервер и другое устройство, но не
  локальную БД редактора. **Добавлены** тесты локальной БД (см. выше).

- **Замечание (Low, отложено)** — лимит pull дневника `.limit(1000)` в
  `SupabaseDiaryBackend.pull()` без порядка по `updated_at` — при >1000 записей часть
  может не дойти; для текущих объёмов некритично.

### I. Дубль записи «один в один» (двойное сохранение, 2026-09-02)
- Симптом: одна запись → после синка на устройстве/обоих устройствах две идентичные копии («один в один»).
- Где смотреть: `_AddEntryScreen._save()` (`diary_screen.dart:1789`), источник — двойной/повторный тап «Сохранить» до `Navigator.pop`.
- Инвариант: каждый `addEntry` при `uuid == null` генерирует **новый** uuid (`diary_provider.dart:124` `_uuid.v4()`). Повторный `_save` → второй uuid → строка-дубль. У обоих устройств (клиент partial unique `(uuid)`, сервер `unique(user_id, uuid)`) дубль с ОДНИМ uuid невозможен — значит «один в один» = **два разных uuid**.
- Проверка: `addEntry` с тем же uuid возвращает `false` и не создаёт вторую строку (unique index `idx_diary_uuid` + `ConflictAlgorithm.ignore`); `addEntry` без uuid при повторе даёт разные uuid (корень, блокируемый UI-guard).
- Фикс: guard `if (_saving) return` + `try/finally { _saving = false }` + дизабл кнопки (`onPressed: _saving ? null : _save`). Покрыто 3 юнит-тестами (группа «ДУБЛЬ», `diary_provider_bugs_test.dart`).
- Как чистить уже созданный дубль: разовая миграция/SQL по `(user_id, содержимое+дата)` с сохранением одной строки — деструктивно, удалять только по явному решению.
