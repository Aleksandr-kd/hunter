### Стратегия монетизации: бесплатный период → подписки (когда появится ИП)

> ⚠️ **Контекст:** сейчас у автора нет ИП, поэтому монетизация не подключается.
> Приложение публикуется бесплатно, всем пользователям открыты **все** функции.
> Позже, когда появится ИП, включаются подписки. **Необходимо сохранить
> «грандфазеринг» (grandfathered)**: пользователям, установившим приложение до даты
> перелома (`T`), навсегда остаются те функции, что они видели в бесплатный период.
> Новым пользователям — по подписке. Это снижает негатив и отвалы.

**Выбрать дату перелома (T):**
- [ ] Зафиксировать дату `T` (момент первого релиза с включёнными подписками)
- [ ] Добавить в `profiles` (или в `subscriptions`) поле даты создания аккаунта / установки, чтобы отличать «до `T`» и «после `T`»

**Грандфазеринг (один раз, на стороне бэкенда Supabase):**
- [ ] Для всех пользователей, зарегистрированных до `T`, проставить в таблице `subscriptions` `/ profiles` `tier = 'max'` (или `grandfathered = true`) — **раз и навсегда**
- [ ] Убедиться, что `expires_at` для grandfathered не ставится (или ставится на 2030+), чтобы логика `AuthProvider.loadSubscription()` не сбрасывала их в `none` по просрочке
- [ ] Новым пользователям (после `T`) — `tier = 'none'`, обычные лимиты

**Код (клиент) — почти не меняется, т.к. гейтинг уже заложен:**
- [ ] Уже есть: `AuthProvider.loadSubscription()` читает `tier` из Supabase и применяет `isPremium` / `isMax`, лимиты дневника, тёмную тему
- [ ] Для grandfathered `tier='max'` — приложение автоматически даст все функции без подписки
- [ ] Для новых `tier='none'` — включить кнопки подписки (см. «Интеграция RuStore SDK» ниже)

**Проверки перед выпуском обновления с подписками:**
- [ ] Старый пользователь (до `T`): видит все функции, кнопки «Подключить» скрыты/неактивны
- [ ] Новый пользователь (после `T`): видит лимиты и кнопки подписки
- [ ] `flutter analyze` и `flutter test` — без ошибок
- [ ] Обновление выкатывается как обычный релиз в RuStore (без удаления данных)

## Найденные и исправленные баги (QA-аудит 2026-08-31)

> Все 4 бага найдены в повторном регресс-QA по коду (`bug_audit_report.txt`),
> подтверждены и исправлены. Связаны с синхронизацией дневника/фото и тарифами.
- **БАГ #4 (High)** — потеря `photoUrl` при редактировании записи + upload без `upsert:true`:
  `_AddEntryScreen._save()` не пробрасывал `photoUrl` → `photo_url` писался в `null`
  локально и на сервере (upsert затирал), `storage.upload` на существующий объект падал 409.
  → фото не обновлялось на другом устройстве. Исправлено:
  проброс `photoUrl: widget.initial?.photoUrl`, `upload(..., upsert: true)`,
  не пушить `photo_url: null` при «фото не меняли».
- **БАГ #1 (Medium)** — «воскрешение» удалённой записи: `_saveKnown(remoteUuids)` не включал
  uuid запушенных в этом цикле записей → запись, удалённая на другом устройстве до второго
  pull, снова заливалась на сервер. Исправлено: known-кэш объединяется с uuid запушенных записей.
- **БАГ #2 (Latent)** — `TierManager.tier` не сбрасывался при `signOut` → утечка Premium/Max
  в лимитах регионов у нового пользователя/гостя. Исправлено: сброс `TierManager.tier = 'none'`
  при событии `signedOut`.
- **БАГ #3 (Minor/Medium)** — `_fromRemote` ставил `photoPath` = серверный URL → ложное
  «без фото» в UI при сбое скачивания и рассинхрон счётчика «с фото». Исправлено: `photoPath = null`
  (фото качается только через `_syncPhoto`).

## БАГ P1-2 (исправлен 2026-09-01) — удаление документов с сервера по title

> Найден в повторном QA-аудите (2026-09-01), подтверждён, исправлен.
> Связан с синхронизацией документов между устройствами.

- **БАГ P1-2 (Medium)** — `DocumentProvider.syncWithServer` удалял с сервера записи
  `user_documents` по совпадению `title` (`remoteTitles.difference(localTitles)`).
  В сочетании с шагом «добавить новые документы с сервера» это могло удалить запись,
  добавленную на другом устройстве, или «воскресить» удалённый документ при
  рассинхроне удаления. Исправлено (2026-09-01) через tombstone: введён список
  удалённых id (`_deletedIds`, SharedPreferences), `deleteDocument` помечает id в
  tombstone, `syncWithServer` удаляет с сервера только id из tombstone (и не
  добавляет их обратно). Чистая функция `remoteIdsToDelete` покрыта юнит-тестами.

## БАГ #1 (исправлен 2026-09-01) — смена фото в существующей записи не синхронизируется

> Найден в регресс-QA (2026-09-01), подтверждён, исправлен.
> Связан с синхронизацией фото дневника между устройствами.

- **БАГ #1 (Critical)** — при редактировании записи и замене фотографии новый файл
  загружался в storage, но `photoUrl` в БД не обновлялся (оставался старый URL).
  `DiaryProvider._uploadEntry()` и `DiarySyncEngine._uploadEntry()` вычисляли
  `resolvedPhotoUrl` заново из старого `entry.photoUrl` вместо использования нового
  URL из `_pushWithPhoto()`.
  → Исправлено: добавлен `copyWith()` в `DiaryEntry`, `_pushWithPhoto()` обновляет
  `entry.photoUrl` через `copyWith` перед отправкой, `_uploadEntry()` использует
  уже обновлённый `photoUrl`. Удалён дублирующий код `resolvedPhotoUrl`.
  → Добавлены 4 юнит-теста: смена фото, без смены фото, добавление фото, copyWith.

## БАГ #1b (2026-09-01) — фото не обновляется на другом устройстве без выхода из аккаунта

> Найден при ручном тестировании после исправления БАГ #1.
> Данные на сервере правильные, но realtime не срабатывает — фото обновляется
> только после выхода и повторного входа (когда DiaryProvider инициализируется заново).

- **БАГ #1b (Medium)** — после upload записи с новым фото realtime-событие не
  доходит до других устройств (возможно из-за RLS-политик Supabase). Фото
  обновляется только при холодном старте приложения (выход → вход).
  → Исправлено: в `DiaryProvider._uploadEntry()` добавлен `unawaited(syncWithServer())`
  после успешного upload — pull с сервера гарантированно обновляет данные на всех
  устройствах, независимо от realtime.
