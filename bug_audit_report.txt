BUG #1: Серверный триггер переписывает updated_at при INSERT
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/diary_provider.dart (строки ~240-260)
Описание:       При push-фазе синхронизации локальные записи отправляются на
                сервер через bulk upsert. В payload включается updated_at, но
                серверный триггер из миграции 0007 (set_diary_updated_at)
                срабатывает только на UPDATE, не на INSERT. Для новых записей
                updated_at устанавливается в now() сервером, игнорируя
                клиентское значение. Это ломает LWW (Last-Write-Wins) conflict
                resolution при синхронизации между устройствами.
Причина:        Серверный триггер перезаписывает updated_at на now() при INSERT.
                Клиент отправляет updated_at в payload, но сервер его игнорирует.
Влияние:        Cross-device conflict resolution сломан. Изменения с Device A,
                сделанные после синка, могут быть перезаписаны более старой
                версией с Device B.
Рекомендация:   В ON CONFLICT (uuid) DO UPDATE явно добавить
                SET updated_at = EXCLUDED.updated_at, чтобы клиентское значение
                сохранялось. Либо убрать updated_at из upsert payload и
                позволить серверу управлять им, но тогда клиент должен
                использовать другую стратегию (например, local clock с offset).

BUG #2: Удаление локальных записей без проверки локального updated_at
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/diary_provider.dart (строки ~210-220)
Описание:       В фазе удаления синхронизации локальные записи, UUID которых
                был известен на сервере, но отсутствует в текущем удалённом
                наборе, удаляются локально. Это происходит ДО push-фазы.
                Если запись создана на Device A, отправлена на сервер, затем
                удалена пользователем на Device C, то при следующем синке
                Device A удалит эту запись локально — хотя она была создана
                локально и должна была сохраниться до подтверждения.
Причина:        Логика обнаружения удаления
                (_knownRemoteUuids.contains(e.uuid) && !remoteUuids.contains(e.uuid))
                не учитывает случай, когда локальное устройство является
                создателем записи, а удаление произошло на другом устройстве.
Влияние:        Потеря данных при использовании нескольких устройств. Запись,
                созданная на Device A, может быть удалена локально, если
                пользователь удалил её на Device C.
Рекомендация:   Отслеживать записи, созданные локально с момента последнего
                синка. Удалять локально только если серверное удаление новее
                локального времени создания.

BUG #3: Гонка между локальной вставкой и удалённым аплоадом в addEntry
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/diary_provider.dart (строки ~78-86)
Описание:       Метод addEntry вызывает _db.insertDiaryEntry синхронно, затем
                вызывает await load() для обновления UI. Одновременно
                unawaited(_uploadEntry(...)) запускается в фоне. Если
                пользователь быстро добавляет несколько записей, каждая
                запускает фоновую загрузку. load() после каждой вставки
                обновляет _entries из локальной БД, но UI может показывать
                устаревшие данные, если syncWithServer() запущена параллельно.
Причина:        Нет синхронизации между локальным путём записи и фоновым
                путём удалённой загрузки. Флаг _syncRunning защищает только
                syncWithServer(), но не addEntry/updateEntry.
Влияние:        UI показывает устаревшие записи при быстром добавлении.
                Фоновые аплоады могут конфликтовать друг с другом.
Рекомендация:   Очередь аплоадов и блокировка записи для сериализации локальных
                записей и удалённых аплоадов. Использовать write lock или
                StreamController для сериализации.

BUG #4: Статический флаг _initialized не thread-safe
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/services/supabase_service.dart (строки ~52-57)
Описание:       Статический bool _initialized проверяется и устанавливается без
                синхронизации. Если init() вызывается параллельно из разных
                async-контекстов, оба могут увидеть _initialized == false и
                оба вызвать Supabase.initialize(), что приведёт к гонке.
Причина:        Нет sync-ключа или мьютекса, защищающего флаг _initialized.
Влияние:        Потенциальная double-initialization Supabase клиента, что может
                вызвать ошибку или undefined behavior.
Рекомендация:   Использовать Completer<void> для синхронизации инициализации:
                static final _initCompleter = Completer<void>();
                static Future<void> init() async {
                  if (_initialized) return;
                  // ...
                  await _initCompleter.future;
                }

BUG #5: AppDatabase создаётся per-provider, но не диспозится
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/diary_provider.dart (строка 27)
Описание:       DiaryProvider создаёт новый экземпляр AppDatabase() в
                конструкторе, но никогда не вызывает close() для базы данных.
                AppDatabase использует статический синглтон для Database
                экземпляра, но wrapper-объект создаётся каждый раз и не
                очищается. При recreation DiaryProvider (например, hot restart)
                старые экземпляры собираются GC, но статический _db остаётся.
Причина:        DiaryProvider не реализует dispose() для закрытия БД.
Влияние:        Утечка ресурсов. На Android могут накапливаться SQLite
                database handles. На iOS могут исчерпаться file descriptors
                при интенсивном использовании.
Рекомендация:   Либо сделать AppDatabase истинным синглтоном с явным close(),
                либо вызывать AppDatabase.close() в DiaryProvider.dispose().

BUG #6: updateEntry не проверяет entry.id перед обновлением в БД
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/diary_provider.dart (строки ~101-108)
Описание:       updateEntry передаёт entry напрямую в _db.updateDiaryEntry(entry).
                Метод AppDatabase.updateDiaryEntry использует entry.id в WHERE
                clause (where: 'id = ?', whereArgs: [entry.id]). Если entry.id
                равен null (что может произойти, если запись создана локально,
                но ID не был назначен), обновление молча fails без ошибки.
Причина:        Guard if (entry.id == null) return предотвращает попадание null
                ID в БД, но вызывает это молча — данные теряются.
Влияние:        Тихая потеря данных. Обновления записей с null ID молча
                пропускаются.
Рекомендация:   Логировать warning при entry.id == null. Гарантировать, что
                _AddEntryScreen всегда передаёт корректный ID.

BUG #7: _knownRemoteUuids не популируется при первом синке
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/diary_provider.dart (строки ~56-63)
Описание:       _knownRemoteUuids загружается из SharedPreferences при
                конструировании. При первом синке заполняется remoteUuids в
                конце syncWithServer. Однако если у пользователя есть локальные
                записи, которые никогда не синхронизировались (без UUID), и
                затем сервер имеет записи, удалённые на другом устройстве,
                обнаружение удаления не сработает корректно, потому что
                _knownRemoteUuids содержит только UUID из предыдущего синка.
Причина:        _knownRemoteUuids — это snapshot предыдущего синка. Не включает
                записи, добавленные на сервер после последнего синка, но до
                текущего.
Влияние:        Записи, удалённые на одном устройстве, могут не удалиться на
                другом, если пользователь не синхронизировался недавно.
Рекомендация:   В фазе обнаружения удаления использовать текущие remoteUuids из
                текущего синка как источник истины, а не _knownRemoteUuids.
                Или отслеживать удаления через Realtime events.

BUG #8: DocumentProvider удаляет удалённые документы без проверки локальных изменений
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/document_provider.dart (строки ~110-125)
Описание:       Во время синка документы, существующие на сервере, но не
                локально, удаляются с сервера. Локальный список документов
                загружается из SharedPreferences (простое key-value хранилище),
                и серверные документы синхронизируются в локальный список.
                Если пользователь удаляет документ локально (не включая его в
                локальный список), он удаляется с сервера. Нет возможности
                «soft delete» или сохранить документ на сервере.
Причина:        Логика синхронизации однонаправленная: local — источник истины
                для существования документа. Нет концепции «хочу на сервере,
                но не локально».
Влияние:        Если пользователь случайно удалит название документа из
                локального списка, оно будет удалено с сервера и будет
                невосстановимо.
Рекомендация:   Добавить флаг «deleted» для документов вместо физического
                удаления. Или синхронизировать только документы с установленными
                датами истечения.

BUG #9: DocumentProvider использует матчинг по title — хрупко
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/document_provider.dart (строки ~93-100)
Описание:       Документы матчатся по title строке. Если default title
                изменяется (например, «Охотничий билет» переименовывается в
                «Охотничий билет (новый)»), все существующие документы на
                сервере становятся orphaned, и локально создаются новые
                пустые документы.
Причина:        Default document titles захардкожены в _loadLocal. Любое
                изменение этих строк ломает маппинг между локальными и
                удалёнными документами.
Влияние:        Потеря данных при изменении default titles. Серверные документы
                становятся недоступными.
Рекомендация:   Использовать stable IDs для default документов вместо
                полагания на title строки.

BUG #10: AuthProvider.loadSubscription не обрабатывает истёкшие подписки при старте
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/auth_provider.dart (строки ~91-107)
Описание:       При запуске приложения loadSubscription вызывается, что читает
                tier с сервера. Однако если Supabase клиент ещё не
                инициализирован (гонка с SupabaseService.init() в main.dart),

Влияние:        Пользователь может получить premium функции без оплаты, если
                приложение запускается до готовности Supabase.
Рекомендация:   Очередь загрузки подписки до готовности Supabase. Или проверять
                SupabaseService.isReady перед вызовом loadSubscription.

BUG #11: Realtime subscription не чистится при смене auth state
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/diary_provider.dart (строки ~310-320)
Описание:       При изменении auth state (пользователь выходит, затем входит
                снова), _setupRealtime вызывается, что вызывает listenRealtime().
                listenRealtime() отписывается от предыдущего канала и создаёт
                новый. Однако старый subscription не awaited перед созданием
                нового, что может привести к кратковременному периоду, когда
                два канала подписаны на данные одного и того же пользователя.
Причина:        _realtimeSub?.unsubscribe() вызывается без await, новый
                сабскрайб создаётся немедленно.
Влияние:        Утечка памяти от не полностью очищенных каналов. Дубликаты
                событий в кратковременный период overlap.
Рекомендация:   Await unsubscribe перед созданием нового subscription.

BUG #12: DiaryEntry.fromMap падает на null date поле
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/models/diary_entry.dart (строка 54)
Описание:       DateTime.parse(map['date'] as String) выбросит исключение, если
                map['date'] равен null. Схема БД имеет date TEXT NOT NULL, так
                что это не должно происходить для валидных записей. Однако если
                в БД существует повреждённая запись, это выбросит исключение и
                крашнет весь getDiaryEntries().
Причина:        Нет null check или fallback для date поля.
Влияние:        Краш приложения при наличии повреждённой diary entry в БД.
Рекомендация:   Использовать DateTime.tryParse() с fallback на DateTime.now().

BUG #13: Синхронизация не обрабатывает ошибки аплоада фото gracefully
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/diary_provider.dart (строки ~280-310)
Описание:       При аплоаде фото, если аплоад fails (например, network error,
                storage quota exceeded), entry всё равно upsertится в таблицу
                diary_entries без photo_url. Entry появляется на сервере, но
                без фото. При следующем синке entry обновится локально, но фото
                всё ещё отсутствует, и цикл повторяется.
Причина:        Photo upload и entry upsert в одном try-catch блоке. Если
                photo upload fails, entry всё равно upsertится без photo URL.
Влияние:        Фото молча теряются. Данные пользователя частично синхронизируются.
Рекомендация:   Upsert entry сначала, затем аплоадить фото отдельно. Если
                аплоад фото fails, пометить entry как имеющую unsynced photo
                и retry при следующем синке.

BUG #14: SettingsSyncProvider может вызвать infinite notification push loop
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/settings_sync_provider.dart (строки ~70-78)
Описание:       setNotifications вызывает _saveNotifications() (запись в
                SharedPreferences), затем вызывает pushToServer(). Если сервер
                push succeeds, applyFromServer() запущенный Realtime update
                прочитает те же значения обратно. Однако _applying установлен
                только внутри applyFromServer, не при initial setNotifications
                вызове. Если серверный push триггерит Realtime event перед
                тем, как _applying будет установлен, это может вызвать loop.
Причина:        Флаг _applying установлен внутри applyFromServer, но Realtime
                listener fires loadSubscription() (который вызывает notifyListeners())
                независимо.
Влияние:        Потенциальный infinite loop push настроек, если Realtime events
                fires rapidly.
Рекомендация:   Установить _applying = true перед вызовом pushToServer() и
                очистить после завершения applyFromServer().

BUG #15: AnalyticsService.calculateTrend имеет off-by-one в границах периода
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/services/analytics_service.dart (строки ~110-115)
Описание:       Текущий период начинается с DateTime(now.year, now.month - 2, 1),
                что является 2 месяца назад. Но сравнение использует
                isAfter(currentPeriodStart.subtract(const Duration(days: 1))),
                что означает, что записи за день до начала периода включаются.
                Это эффективно расширяет период на один лишний день с каждой
                стороны, приводя к double-counting записей на границе.
Причина:        subtract(Duration(days: 1)) предназначен для включения boundary
                дня, но в сочетании с isBefore(currentPeriodEnd.add(...)) на
                другой стороне создаёт overlap.
Влияние:        Расчёты тренда могут показывать слегка завышенные числа на
                границах периодов.
Рекомендация:   Использовать isAfter без day offset для start boundary и
                isBefore без day offset для end boundary.

BUG #16: NotificationService планирует уведомления каждый раз при вызове _init
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/services/notification_service.dart (строки ~16-28)
Описание:       _init() вызывается в конструкторе, но нет guard для предотвращения
                re-initialization. Если NotificationService.instance доступ
                несколько раз (например, в тестах или при перезапуске приложения),
                _init() вызывается несколько раз, что может вызвать дубликаты

Причина:        Флаг _initialized проверяется в isReady, но _init() сам не
                проверяет его перед выполнением.
Влияние:        Дубликаты notification channels на Android. Несколько
                FlutterLocalNotificationsPlugin instances могут конфликтовать.
Рекомендация:   Добавить guard в начало _init(): if (_initialized) return;

BUG #17: Notification IDs SeasonsProvider могут коллидовать
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/seasons_provider.dart (строки ~190-195)
Описание:       Notification IDs вычисляются как
                (hash.abs() % 100000) * 100 + (type == 'open' ? 10 : 20) + days.
                Поскольку hash только modulo 100000, и multiplier равен 100,
                effective range равен 0-9,999,900 с шагом 100. Если две
                разные записи имеют одинаковый hash modulo 100000, они получат
                одинаковый notification ID, заставляя один перезаписать другой.
Причина:        Hash modulo слишком мал относительно количества возможных записей.
Влияние:        Некоторые season notifications могут быть молча перезаписаны
                другими.
Рекомендация:   Использовать более robust ID generation, например
                hash.abs() % 10000000 или UUID-based подход.

BUG #18: Миграция AppDatabase v6 не обрабатывает существующие данные корректно
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/db/app_database.dart (строки ~60-66)
Описание:       Миграция устанавливает updated_at = date для всех записей, где
                updated_at IS NULL. Однако date поле — это полный DateTime
                (включая время), в то время как updated_at должен идеально
                захватывать actual last-modified time. Если записи были созданы
                с date в прошлом, но модифицированы недавно, updated_at будет
                некорректно отражать дату создания, ломая LWW conflict resolution.
Причина:        Миграция использует date как fallback для updated_at, но date
                представляет дату охоты, а не время модификации.
Влияние:        Записи, модифицированные после создания, будут иметь stale
                updated_at значения, вызывая incorrect conflict resolution
                во время синхронизации.
Рекомендация:   Использовать DateTime.now() как fallback value вместо date.

BUG #20: _knownRemoteUuids может расти неограниченно
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/diary_provider.dart (строки ~56-63)
Описание:       _knownRemoteUuids хранит все UUID удалённых diary entries.
                Со временем, когда записи удаляются с сервера, но UUID
                остаются в _knownRemoteUuids, set растёт. Если пользователь
                использует приложение годами с множеством записей, этот set
                может стать большим.
Причина:        UUID удаляются только при локальном удалении записи.
Влияние:        Увеличение memory usage со временем. SharedPreferences string
                может стать очень большим.
Рекомендация:   Периодически чистить _knownRemoteUuids путём сравнения с
                текущими серверными данными.

BUG #21: DocumentProvider sync не обрабатывает network errors во время upload
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/document_provider.dart (строки ~145-165)
Описание:       Если _uploadDocument fails (network error), local state уже
                обновлён (_documents[idx] = ...copyWith(...)) и _saveLocal()
                уже вызван. Ошибка только logged через debugPrint. Пользователь
                видит updated UI, но сервер всё ещё имеет старые данные.
Причина:        Local state обновляется перед удалённым аплоадом.
Влияние:        UI показывает updated данные, которые ещё не на сервере. Если
                приложение крашится до следующего синка, пользователь может
                потерять обновление.
Рекомендация:   Очередь обновления и применять к local state только после
                успешного remote upload.

BUG #22: RegionsRepository использует DateTime.now().year для season dates
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/data/regions_repository.dart (строки ~17-45)
Описание:       Season dates вычисляются с использованием
                DateTime(DateTime.now().year, ...). Это означает, что даты
                пересчитываются каждый раз при вызове getRegions(). Если
                приложение открыто в декабре, даты для сезонов следующего
                года будут неверными (они используют текущий год, а не
                следующий).
Причина:        Даты вычисляются dynamically вместо того, чтобы быть static.
Влияние:        Даты сезонов могут быть неверны для cross-year сезонов
                (например, сезон с ноября по январь).
Рекомендация:   Вычислять даты один раз при запуске приложения и кэшировать их.

BUG #23: DiaryScreen использует DateTime.now().microsecondsSinceEpoch как Dismissible key fallback
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/screens/diary_screen.dart (строка ~343)
Описание:       ValueKey(e.id ?? e.uuid ?? DateTime.now().microsecondsSinceEpoch)
                использует DateTime.now().microsecondsSinceEpoch как fallback
                key. Поскольку это оценивается во время widget build, каждый
                rebuild создаёт новый key, заставляя Dismissible widget
                rebuild с новым key, что сбрасывает его состояние (swipe
                position, animation).
Причина:        DateTime.now() вызывается в build method, не в data model.
Влияние:        Dismissible widgets могут flicker или сбрасывать состояние на
                каждом rebuild.
Рекомендация:   Использовать stable identifier. Если оба id и uuid null,
                запись не должна отображаться (invalid data).

BUG #24: SettingsSyncProvider.pushToServer отправляет два отдельных upsert для одной row
────────────────────────────────────────────────────────────────────────────────
Файл:           lib/providers/settings_sync_provider.dart (строки ~135-155)
Описание:       pushToServer сначала upsertит theme_mode и enabled_regions,
                затем upsertит notifications_seasons и notifications_documents
                в отдельном вызове. Оба upsert targeting same user_id row.
                Если первый upsert succeeds, но второй fails, настройки
                частично синхронизируются.
Причина:        Два отдельных upsert вызова для одной row.
Влияние:        Partial settings sync. Theme и regions могут быть sync, но
                notifications — нет.
Рекомендация:   Объединить все поля в один upsert вызов.
