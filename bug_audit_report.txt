БАГ #1 — Medium / мульти-устройство: «воскрешение» свежесозданной удалённой
  записи дневника — ИСПРАВЛЕНО
  Файл: lib/providers/diary_provider.dart:411 (saveKnown(remoteUuids))
  Статус: исправлено 2026-08-31 (known-кэш объединяется с uuid запушенных
    в этом цикле записей: toPush + withoutUuid)
  Описание: в syncWithServer кэш известных uuid обновляется как
   await _saveKnown(remoteUuids), где remoteUuids — это uuid из СНАПШОТА,
   полученного на шаге 1 (pull, строки 226-231) ДО пуша локальных записей
   на шаге 3 (строки 336-408). Свежесозданная локальная запись, запушенная
   в этом же цикле, не попадает в _knownRemoteUuids, пока не появится в
   remote-снапшоте при следующем pull.
  Сценарий потери интенции юзера:
   1. Устройство A создаёт запись X офлайн и синкается один раз.
      X запушена на сервер, но НЕ добавлена в _knownRemoteUuids (A).
   2. Устройство B (тот же аккаунт) получает X, юзер удаляет X на B ->
      запись удалена на сервере; на B ушла и из known (у B она была).
   3. На A приходит realtime delete -> hasRemoteChange. Юзер жмёт «Синхронизировать».
      - toDeleteLocal (строка 289-291): условие _knownRemoteUuids.contains(X)
        == false -> X НЕ удаляется локально на A.
      - toPush (строки 336-348): X есть локально, remote нет -> X СНОВА
        заливается на сервер. Запись, которую юзер специально удалил,
        «воскресает».
  Влияние: не потеря данных, но нарушение интенции пользователя при
  многодевices-синхронизации; противоречит заявленному поведению в 2.4
  («удалённая на другом устройстве запись удаляется и локально»).
  Рекомендация: в _saveKnown(remoteUuids) объединять с uuid записей,
  запушенных в текущем цикле (toPush), либо после успешного пуша добавлять
  их в known. Либо хранить known-кэш по результатам push+pull вместе.

БАГ #2 — Latent (проявится при включении монетизации): TierManager не
  сбрасывается при выходе из аккаунта — ИСПРАВЛЕНО
  Файл: lib/providers/auth_provider.dart:64; lib/services/tier_manager.dart
  Статус: исправлено 2026-08-31 (при событии signedOut добавляется
    TierManager.tier = 'none')
  Описание: при signOut в onAuthStateChange выполняется только
   _tier = 'none' (локальное поле AuthProvider), а статический
   TierManager.tier НЕ сбрасывается. При этом RegionsProvider.hasUnlimited
   = TierManager.isMax и maxRegions = TierManager.isMax ? 999 : 1
   (regions_provider.dart:18-19) читают именно статический TierManager.
  Сценарий: юзер с Premium/Max выходит -> на устройстве остаётся гость
   (или входит другой пользователь). Пока loadSubscription не перезапишет
   TierManager.tier (или юзер не входит), старый Premium/Max остаётся
   активным: гость может включить все регионы, считать max регионов и т.п.
  Влияние: сейчас НЕ проявится, т.к. монетизация выключена
   (subscription_screen.dart:19 _showSubscription=false, всё открыто).
   Но при включении платных тарифов это утечка платного статуса.
  Рекомендация: в signOut/onAuthStateChange при событии signedOut
   дополнительно сбрасывать TierManager.tier = 'none'.

БАГ #3 — Minor/Medium, подтверждённый по коду: photoPath = серверный URL в
  _fromRemote (ложное «без фото» в UI при сбое загрузки) — ИСПРАВЛЕНО
  Файл: lib/providers/diary_provider.dart:632; UI diary_screen.dart:1015,1218;
      analytics_service.dart:124,489; stats_screen.dart:51
  Статус: исправлено 2026-08-31 (в _fromRemote photoPath = null; фото качается
    только через _syncPhoto)
  Описание: _fromRemote присваивает photoPath = r['photo_url'] (серверный
  url, напр. "userid/uuid.jpg") в локальную колонку photo_path. Дальше в том
  же цикле _syncPhoto (строки 581-621) скачивает файл и перезаписывает
  photoPath на настоящий локальный путь (при успехе).
  Реальные последствия при СБОЕ _syncPhoto (нет сети, недоступен storage):
   1. photoPath остаётся серверным URL. UI проверяет
      photoPath != null && File(photoPath).existsSync() -> false
      (diary_screen:1015/1218) => запись показывается БЕЗ фото, хотя на
      сервере фото есть. Аналитика считает "с фото" по photoPath != null
      (stats:51, analytics:124/489) => счётчик «с фото» >= реально отображаемых.
   2. Повторный push в toPush НЕ происходит (LWW: локальная не новее
      серверной) => push-ветка не качает фото.
   3. НО pull-ветка (строки 281-284) на КАЖДОМ syncWithServer заново
      вызывает _syncPhoto для записей с photo_url => БАГ САМОКОРРЕКТИРУЕТСЯ
      при следующем успешном полном синке.
  Потеря данных на сервере НЕ происходит (upsert в plain не передаёт
  photo_url, существующий photo_url не затирается).
  Итог: подтверждаю как баг (Minor/Medium), самокорректирующийся.
  Рекомендация (как в прошлом аудите + уточнено): в _fromRemote ставить
  photoPath=null (а photoUrl=r['photo_url']), фото качать только через
  _syncPhoto. Тогда UI не будет показывать фейковые пути, а счётчик «с фото»
  совпадёт с реальностью.

БАГ #4 — High / реальный, «фото не подхватывается на другом устройстве»:
  потеря photoUrl при редактировании записи + upload без upsert -> затирание
  фото на сервере — ИСПРАВЛЕНО
  Файл: lib/screens/diary_screen.dart:1552-1576 (_AddEntryScreenState._save)
        lib/providers/diary_provider.dart:526-566 (_insertRemote), 537 (upload)
  Статус: исправлено 2026-08-31 (проброс photoUrl в _save; upload с
    upsert:true; photo_url не обнуляется при отсутствии локального файла)
  Стек: supabase_flutter ^2.8.0 (pubspec.yaml:53)
  Описание: _save() при редактировании собирает DiaryEntry БЕЗ поля photoUrl
   (не пробрасывает widget.initial?.photoUrl). Дальше:
   1) updateEntry -> updateDiaryEntry (app_database.dart:135-142) пишет в
      локальную БД photo_url = null (entry.photoUrl == null).
   2) _uploadEntry -> _insertRemote: если File(photoPath).existsSync():
      storage.upload(objName, file) вызывается БЕЗ upsert:true (строка 537).
      В supabase_flutter 2.x upload по умолчанию upsert=false -> при
      существующем объекте "userid/uuid.ext" кидает StorageException
      (409/дубликат) -> catch -> photoUrl = null.
   3) Затем upsert с 'photo_url': null (строка 554) -> на СЕРВЕРЕ фото
      затирается на null (onConflict user_id,uuid обновляет колонку).
   4) На устройстве B: pull видит photo_url = null -> _syncPhoto не
      вызывается (rPhoto == null) -> B не показывает/не обновляет фото.
  Симптом пользователя: «добавляю/меняю фото в записи — на другом устройстве
   не отрабатывает» — воспроизводится каждый раз, когда расширение то же
   (jpg->jpg) ИЛИ фото есть локально (File.existsSync() true).
  Влияние: потеря интенции юзера (фото не доезжает), на сервере фото
   обнуляется. Затрагивает самый частый сценарий работы с фото.
  Рекомендация:
   - В _save() пробрасывать photoUrl: widget.initial?.photoUrl в DiaryEntry
     при редактировании (и сохранять photo Path строкой, без обнуления при
     «не трогали фото»).
   - В _insertRemote загружать фото ЧЕРЕЗ storage.upload(..., upsert: true)
     (или генерировать уникальное имя объекта), чтобы замена фото
     перезаписывала объект, а не падала и не роняла photo_url в null.
   - Не пушить photo_url: null в upsert, если фото не меняли (иначе затирает
     на сервере).
