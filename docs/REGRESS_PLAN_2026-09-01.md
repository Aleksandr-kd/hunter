### НОВЫЙ БАГ #1 (ИСПРАВЛЕН): Смена фото в существующей записи не синхронизируется

**Серьёзность:** 🔴 Критический → ✅ Исправлен
**Компонент:** `lib/providers/diary_provider.dart`, `lib/providers/diary_sync_engine.dart`, `lib/models/diary_entry.dart`

**Описание:**
При редактировании существующей записи и замене фотографии новый файл загружается на сервер, но `photoUrl` в базе данных **не обновляется**.

**Причина:** `_uploadEntry()` в обоих файлах вычислял `resolvedPhotoUrl` заново из старого `entry.photoUrl` вместо использования нового URL из `_pushWithPhoto()`.

**Исправление:**
1. Добавлен метод `copyWith()` в `DiaryEntry` для создания копии с обновлённым `photoUrl`
2. `_pushWithPhoto()` в `DiarySyncEngine` теперь обновляет `entry.photoUrl` через `copyWith` перед отправкой на сервер
3. `_uploadEntry()` в обоих файлах теперь использует `entry.photoUrl` который уже содержит новый URL
4. Удалён дублирующий код вычисления `resolvedPhotoUrl` из старого URL
5. Удалён unused import `dart:io` из `diary_provider.dart`

**Результат:** При смене фото новый URL корректно записывается в БД и синхронизируется между устройствами.

**R2 (новое, низкий приоритет):** в форме редактирования **нет отдельного действия
«удалить фото»** — фото можно только заменить через «Добавить фото»
(`diary_screen.dart:1956-1958`). Если пользователь хочет убрать фото из записи,
единственный путь — заменить на другое. Не блокирует релиз.

**R3 (низкий приоритет, по коду):** в `DocumentProvider._uploadDocument`
(`document_provider.dart:290-292`) при **сбросе** даты (expiry=null) флаг локально
изменённого `_lastModified[title]` сознательно НЕ снимается (защита от «воскрешения»
сброшенной даты). Следствие: каждую синхронизацию запись с только что сброшенной
датой повторно пушится `expiry_date:null` на сервер. Безопасно (конвергентно по LWW),
но лишний upsert до следующего изменения. Не блокирует релиз.

**R4 (низкий приоритет):** LWW использует строгое сравнение `isAfter`
(`diary_sync_engine.dart`). При одновременном редактировании одной записи на двух
устройствах с одинаковой микросекундной меткой возможно, что ни одна не считается
новее (не будет «воскрешения», но локальное изменение второго устройства не уедет
до следующего изменения). Вероятность крайне мала.

**R5 (не блокирует):** нет unit-тестов на `DocumentProvider`, `SettingsSyncProvider`,
`RegionsProvider` (лимит регионов), `AuthProvider` (просрочка тарифа), `LockProvider`,
и нет виджет-тестов на гейтинг по тарифу (сейчас функции открыты). Рекомендуется
добавить перед включением монетизации.

**R6 (по коду, информационно):** `AuthProvider._listen` при `!SupabaseService.isReady`
сразу ставит `guest` и `notifyListeners()` — после чего `loadSubscription` не
вызывается (нечего загружать). Поведение offline корректно.

**БАГ #3 (Medium, исправлен) — локальный `photo_url` не обновляется после смены фото.**

Цепочка вызова (проверено по коду):
`diary_screen.dart:_save()` при смене фото передаёт `photoUrl: null` →
`DiaryProvider.updateEntry()` (`diary_provider.dart:135`) пишет в БД `photo_url=null`
и ставит в очередь `_uploadEntry(fresh)`, где `fresh` перечитан из БД (тоже `photo_url=null`) →
`DiarySyncEngine._uploadEntry()` (`diary_sync_engine.dart:543`) вызывает `_pushWithPhoto(entry)`.
В `_pushWithPhoto()` (`diary_sync_engine.dart:440`) новый URL получается так:
```dart
final updatedEntry = entry.copyWith(photoUrl: photoUrl);
await backend.pushEntry(updatedEntry, photoUrl);
return true;
```
`updatedEntry` — это **локальная переменная**; наружу `_pushWithPhoto` возвращает только `bool true`,
а исходный `entry` НЕ мутируется. Поэтому в `_uploadEntry()` строка `photoUrl: entry.photoUrl`
пишет в локальную БД прежний `null`, а не новый URL. Тот же эффект в цикле `sync()`
(`diary_sync_engine.dart:375-401`): после `_pushWithPhoto(e)` в БД пишется `photoUrl: e.photoUrl`.

Проявление:
- Сервер получает правильный новый `photo_url` (upsert с новым URL) ✅.
- Другое устройство при pull получает верный URL через `_syncPhoto` ✅.
- На устройстве-редакторе локальная БД остаётся с `photo_url = null` ❌; фото в UI
  показывается по `photoPath` (новый локальный файл), поэтому внешне не заметно.
- Т.к. `_uploadEntry` ставит `updated_at = now`, локальная запись навсегда остаётся
  «свежее» серверной → каждый `sync()` повторно загружает то же фото и повторно его
  скачивает через `_syncPhoto`. Избыточная нагрузка + постоянное несоответствие
  локальной БД и сервера до следующего изменения.

Влияние на данные: **потеря фото/данных отсутствует** (сервер и другие устройства
корректны). Баг снижает согласованность локальной БД и генерирует лишние сетевые
операции.

**Исправление (применено):** `_pushWithPhoto` теперь возвращает `Future<DiaryEntry?>`
(обновлённую запись с актуальным `photoUrl`), публичный `pushEntry` остался `bool`,
добавлен `pushEntryWithPhoto()`. `_uploadEntry()` (engine) и цикл `sync()` пишут в БД
`updated.photoUrl` из возвращённой записи; `DiaryProvider._uploadEntry` использует
`pushEntryWithPhoto`. Покрыто: `test/providers/diary_provider_bugs_test.dart` (2 теста).

**БАГ #5 (Medium, исправлен) — фото не обновляется на устройстве после смены на другом (кэш Image).**

Сценарий: смена фото на Android → сервер корректен → на iPhone после нажатия
«Синхронизировать» фото НЕ меняется; помогает только выход/вход из аккаунта.

Причина: `_syncPhoto` (`diary_sync_engine.dart:471`) скачивает новое фото и перезаписывает
файл по **тому же** пути `$uuid.$ext` (`diary_sync_engine.dart:491`). А карточка записи
рендерится `Image.file(File(entry.photoPath!))` (`diary_screen.dart:1306`) — Flutter
кеширует декодированный кадр по пути файла, идентичность пути → старый кадр не
перерисовывается. При выходе/входе виджет-дерево пересоздаётся → кэш сброшен → видно новое.

**Исправление (применено):** топ-левел `photoCacheKey(DiaryEntry)` в `diary_screen.dart`
используется как `ValueKey` у `Image.file` (зависит от `photoUrl`, fallback на `photoPath`)
+ `gaplessPlayback: true`. Смена `photoUrl` → пересоздание виджета → актуальный кадр.
Покрыто: `test/screens/diary_photo_cache_test.dart` (2 теста).

**БАГ #6 (Medium, исправлен) — файл фото из image_picker остаётся во временном кэше приложения.**

Сценарий: после чистки кэша приложения фото из записи «исчезало» вовсе; восстанавливалось
только после ручной синхронизации.

Причина: `image_picker.pickImage()` кладёт файл во временный кэш приложения (cacheDir), а
`_save()` (`diary_screen.dart:1587`) сохранял `picked.path` как `photo_path`. Android может
очистить кэш → `File(photoPath).existsSync()` = false → `hasPhoto` = false (`:1015`) → фото
«исчезает», пока `_syncPhoto` не скачает файл в `documents/diary_photos`.

**Исправление (применено):** добавлен `lib/data/photo_persist.dart` —
`persistPickedPhoto(srcPath)` копирует выбранный файл в `documents/diary_photos` сразу в
`_pickPhoto()` (`diary_screen.dart`), поэтому `photoPath` всегда указывает на долговременный
файл, переживающий чистку кэша. Покрыто: `test/data/photo_persist_test.dart` (2 теста).

**БАГ #7 (High, исправлен 2026-09-01) — фото не обновляется на другом устройстве до перелогина.**

Сценарий: смена фото на Android → синхронизация → на iPhone фото НЕ обновляется; помогает
только выход/вход (перелогин сбрасывает локальные записи, и `_syncPhoto` с `photoPath == null`
вынужден качать).

Причина: URL фото **фиксирован** для записи — `uploadPhoto()` возвращает
`objName = 'user/<uuid>.<ext>'` (`_pushWithPhoto`), а uuid не меняется при перезаписи. Поэтому
ни LWW (серверный `photo_url` == локальному → URL не меняется), ни гейт `_syncPhoto` (по
`e.photoUrl == photoUrl` — после LWW URL совпадает, а файл `$uuid.$ext` существует → не качает)
не могли обнаружить смену содержимого. `photoCacheKey` по фиксированному URL не менялся → Image
показывал устаревший кадр.

Исправление (применено, 3 точки):
1. `_pushWithPhoto` — в objName вшита версия (`_<мс от updated_at>`) → URL меняется при смене фото.
2. `_syncPhoto` — путь файла `$uuid.$version.$ext`; гейт перекачивает, если файла для ЭТОЙ версии ещё нет (путь не совпал или файл отсутствует).
3. `photoCacheKey` — приоритет `photoPath` (несёт версию) вместо фиксированного URL → `Image` пересоздаётся при новой версии.

Покрыто: обновлён `test/screens/diary_photo_cache_test.dart` (3 кейса: ключ меняется при смене
версии/пути на том же URL; стабилен для одного файла; fallback на URL), ожидания БАГ #3 в
`test/providers/diary_provider_bugs_test.dart` приведены к версионированным URL. Итог:
`flutter analyze` = 0, `flutter test` = 109 зелёных.

Рекомендуется перед выпуском:
1. Прогнать ручной чек-лист 1.1–1.11 на реальном Android + iOS (особенно 1.4 — смена фото).
2. Настроить RuStore-консоль и загрузить AAB (`build/app/outputs/bundle/release/app-release.aab`).
3. При включении монетизации — актуализировать лимит «10 записей» (R1) и добавить тесты (R5).
